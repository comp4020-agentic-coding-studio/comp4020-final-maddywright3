# C10 prompts (Claude Code)

## Build (plan mode)

Read CLAUDE.md, README.md, docs/adr/001-stack.md, docs/adr/002-who-counts-as-here.md
and the current src/ and spec/ first.

This is the C10 milestone ("Fly by instruments"): the app must tell people apart,
check on the server what each person may see and do, and log who did what.
The README's single idea is "you can admit you're lost without being the one who
admitted it". Every change here must serve that.

Telling browsers apart
- On any GET of a lecture page, if there's no valid browser cookie, create a random
  128-bit ID (node:crypto), store it in a new browsers table, and set it as a cookie:
  HttpOnly, SameSite=Lax, Path=/, Secure when the request came over https, long Max-Age.
- A tap or events request whose cookie isn't in the browsers table is rejected (403).
  Check the ID exists, don't just check a cookie is present.
- Migration: add taps.browser_id (nullable for old rows), safe on the existing /data db.

One browser, one voice
- "present" counts unique browser IDs with an open stream, not connections.
  Five tabs in one browser are one person.
- A browser with a tap in the last 60 seconds can't add another. The server ignores it
  and says so (the no-JS form shows "You're already counted").
- Each page shows "You've said you're lost N times in this lecture" for that browser,
  so a person's own trace is still there when they come back.

Privacy
- Remove the list of individual tap times everywhere. Replace it with a timeline of
  taps per minute, formatted in Australia/Sydney time (en-AU), never per person.
- No page, stream or JSON response ever contains a browser ID other than the cookie
  the browser already holds.

Lecturer view
- GET /l/:id/lecturer : without a valid lecturer session, show a form asking for the
  lecture's code. With one, show the live gauge, total, and the per-minute timeline.
- Lecture codes are stored hashed with scrypt (node:crypto), compared in constant time.
  On a correct code, create a random session token in a lecturer_sessions table and set it
  as an HttpOnly, SameSite=Strict cookie scoped to that lecture's path. Fail closed:
  anything unexpected means no access.
- Limit wrong code attempts to 10 per lecture per minute (in memory is fine).
- The demo lecture's code is DEMO. This is deliberately public, so markers can get in.
- GET /new : a form with a lecture title. POST creates the lecture with a random id
  and a random 8-character code, shows the student link and the code once, and never again.

Feedback on a slow connection
- With JavaScript on, the button changes to "Sending..." straight away, then to
  "You're counted" (disabled until the tap fades). If the request fails, restore it
  and show "Couldn't send. Try again."

Logging (read with flyctl logs at the crit)
- One JSON line per action: time, action (page_view, tap, tap_ignored, tap_rejected,
  stream_open, stream_close, lecturer_login_ok, lecturer_login_failed, lecture_created),
  lecture id, and who: the first 8 hex characters of sha256(browser ID).
- Never log raw browser IDs, cookies, codes or session tokens.

Tests in spec/, using inject("baseUrl") and sending cookies by hand:
- two different browser cookies count as two present, two streams with one cookie count as one
- a second tap within 60 seconds from the same browser doesn't change the count
- a tap with no cookie or a made-up cookie is rejected
- /l/demo/lecturer without a session doesn't show the gauge; with the wrong code it still doesn't;
  with DEMO it does
- no student page, lecturer page or stream ever contains a browser ID other than the requester's own
- the per-minute timeline shows Australia/Sydney time
- the existing tests, including the 60-second fade, still pass

Not in scope: accounts, names, editing or deleting lectures.
Commit in small steps with messages saying why. Ask before deploying, pushing or tagging.
Show me the plan first.

## Corrections after reviewing the build

Before pushing, four fixes, each its own commit:

1. Bug: the lecturer cookie is scoped to /l/:id, so it's sent on the student
   page's /l/:id/events too. A lecturer who opens the student page in the same
   browser gets lecturer state there and isn't counted as present. Give the
   lecturer its own stream at /l/:id/lecturer/events, scope the lecturer cookie
   to /l/:id/lecturer, and make /l/:id/events student-only. Add a test: a browser
   holding both cookies gets student state on /l/:id/events and counts as present.

2. Likely crash: decodeURIComponent throws on malformed input (/l/%E0/events,
   or a cookie bid=%E0), and the async server callback has no try/catch, so an
   unhandled rejection could stop the process. Write the test first and show me
   it fails: request /l/%E0, /l/%E0/events and /l/demo with cookie bid=%E0, then
   check / still answers 200. Then fix it: safe decoding (malformed means 400 or
   an unknown cookie), plus a top-level try/catch that returns 500 and logs the error.

3. Now that spec files run one at a time, restore the exact +1 assertion on
   total taps in events.test.ts, and use the shared total again in meter.test.ts
   if it's stable.

4. Add to CLAUDE.md: never loosen an assertion to make a test pass; never rm -rf;
   and a Privacy section (no raw IDs, cookies, codes or tokens in any page, stream,
   response or log; no per-person history; lecturer and student state on separate routes).

## Threshold leak (after the C10 feedback)

Below min_present the gauge text was hidden but the stream still carried the live
count and total. Write the test first and show it failing, then send no tap data
below the threshold to students or the lecturer, and add a CLAUDE.md privacy rule:
hiding it on screen isn't enough.
